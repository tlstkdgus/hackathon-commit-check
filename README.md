# 마감 후 커밋 검사

제출된 깃허브 레포에 **마감 시각 이후 커밋**이 있는지 확인한다.
멋사대학 14기 중앙해커톤 — 결과물 제출 마감 **8/21(금) 09:59:59**,
즉 **10:00:00부터가 마감 후**다.

의존성 없음. `python check.py`로 바로 돈다.

## 준비

**받은 엑셀 파일을 이 폴더에 그대로 넣기만 하면 된다.** 파일명은 아무래도 좋다.

```bash
python check.py --snapshot snapshot-0821.json
```

파일명을 안 적으면 이 폴더에서 `.xlsx` / `.csv` / `.txt`를 찾아 쓴다.
마감 직후에 파일명 오타로 헤매지 않으려는 것이다. 어떤 파일을 골랐는지
`입력 파일: ...`로 알려주고, **후보가 여럿이면 임의로 고르지 않고 멈춘다** —
엉뚱한 파일로 검사하고도 모르는 것보다 낫다.

파일이 다른 곳에 있으면 경로를 적어도 된다.

```bash
python check.py "C:/Users/신상현/Downloads/제출목록.xlsx" --snapshot snapshot-0821.json
```

**열 순서를 맞출 필요가 없다.** 모든 칸을 훑어 깃허브 주소를 찾고, 같은 행에서
주소가 아닌 첫 칸을 팀명으로 쓴다. 첫 열이 '번호'여도 (숫자만 있는 칸은 건너뛰므로)
팀명이 제대로 잡힌다. 머리글·빈 행·메모 행은 조용히 넘어간다.

셀에는 `레포 링크`라고만 보이고 실제 주소가 하이퍼링크에 숨어 있는 경우
(구글시트에서 내보낸 파일이 이렇다) 그 하이퍼링크까지 읽는다.

직접 적을 거라면 텍스트도 된다. 빈 줄과 `#` 주석은 무시한다.

```
# 팀명, 프론트, 백엔드, AI  (팀명은 없어도 됨)
멋사팀, https://github.com/team/front, https://github.com/team/back
https://github.com/other/repo
```

주소는 어떤 형태로 적혀 있어도 읽는다 — `.git` 붙은 것, `/tree/main`이
붙은 것, `git@github.com:` 형태, 그냥 `owner/repo`까지.
프론트·백엔드 칸에 같은 레포를 적은 팀(한 레포로 개발한 경우)은
중복을 제거하고 한 번만 검사한다.

읽지 못한 행은 **경고로 알려준다.** 조용히 빠지면 그 팀이 검사에서
누락된 줄도 모르게 된다.

**토큰이 필요하다.** `gh auth login`이 되어 있으면 그 토큰을 자동으로 빌려
쓴다. 아니면 `GITHUB_TOKEN`을 설정한다. 토큰 없이 돌리면 시간당 60회로
막혀서 600개를 못 돈다.

같은 레포가 여러 번 적혀 있어도(프론트·백엔드 칸에 같은 주소를 넣은 팀)
전체에서 한 번만 검사한다.

## 쓰는 법

### ① 마감 직후 — 스냅샷을 찍는다 (8/21 10:00)

```bash
python check.py repos.txt --snapshot snapshot-0821.json
```

각 레포의 **모든 브랜치 SHA**를 기록한다. 이 파일을 지우면 안 된다.
600개 기준 **2분 안쪽**이면 끝난다 (동시 8개 기준, 실측 40개/8초).

중간에 끊겼다면 같은 명령에 `--resume`을 붙인다. 50개마다 중간 저장하므로
처음부터 다시 돌지 않는다.

```bash
python check.py repos.txt --snapshot snapshot-0821.json --resume
```

### ② 나중에 — 스냅샷과 대조한다

```bash
python check.py --compare snapshot-0821.json --csv result.csv
```

심사 기간 중 아무 때나, 여러 번 돌려도 된다.
600행은 눈으로 못 읽으니 `--csv`로 받아 스프레드시트에서 정렬·분담하는 게 낫다.

### 스냅샷을 못 찍었다면

```bash
python check.py repos.txt
```

커밋 시각만 보는 사후 검사. **아래 한계가 그대로 적용된다.**

## 왜 스냅샷이 필요한가

사후 검사만으로는 **`git push --force`를 잡을 수 없다.**
히스토리를 다시 쓰면 마감 후 커밋이 흔적 없이 사라지고, 남은 커밋은
전부 마감 전으로 보인다. 커밋 날짜도 `git commit --date`로 위조된다.

마감 직후에 SHA를 찍어두면 둘 다 드러난다.

| | 사후 검사 | 스냅샷 대조 |
|---|---|---|
| 마감 후 커밋 추가 | 잡힘 | 잡힘 |
| force-push / rebase | **못 잡음** | 잡힘 |
| 커밋 날짜 위조 | 의심만 표시 | 잡힘 |
| 브랜치 삭제 | **못 잡음** | 잡힘 |

## 600개 규모에서 주의할 것

**마감과 스냅샷 사이에 틈이 생긴다.** 10:00에 시작해도 다 찍는 데 1~2분이
걸리고, 그 사이에 푸시한 팀은 *이미 수정된 상태*로 스냅샷에 들어간다.
그러면 대조로는 영영 안 잡힌다.

그래서 스냅샷에 각 레포의 `pushed_at`을 함께 저장하고, **스냅샷 시점에
이미 마감 후 푸시가 있던 레포를 따로 세어 보고**한다. 스냅샷 직후 출력과
`--compare` 결과 양쪽에 뜬다. 이 목록은 사람이 직접 확인해야 한다.

**API 호출량** — 레포당 약 2회, 600개면 한 번 도는 데 약 1,200회.
토큰이 있으면 시간당 5,000회이므로 **한 시간에 3~4번** 돌릴 수 있다.
남은 호출 수는 리포트 마지막 줄에 찍힌다.

**동시 실행 수**는 `--workers`로 바꾼다(기본 8). 올리면 빨라지지만
깃허브 2차 레이트리밋에 걸리면 오히려 느려진다. 걸리면 모든 워커가
함께 멈췄다가 재개하므로 그냥 두면 된다.

## 파일은 어디에 놓이나

DB 없이 전부 파일이다. 클론한 디렉토리 안에 두면 된다.

| 파일 | 내용 | git |
|---|---|---|
| `submissions.xlsx` / `repos.txt` | 입력 — 팀명·레포 주소 | 제외 |
| `snapshot-0821.json` | **10시 스냅샷** (브랜치 SHA 전부) | 제외 |
| `result.csv` · `report.md` | 검사 결과 | 제외 |

셋 다 `.gitignore`에 있다 — 학생 팀명과 레포 주소가 들어가기 때문이다.
**`snapshot-0821.json`을 지우면 force-push 검사가 통째로 불가능해진다.**

## 결과 읽기

| 표시 | 뜻 |
|---|---|
| `[위반]` | 마감 후 커밋이 실제로 확인됨 |
| `[확인]` | 마감 후 푸시 기록은 있는데 커밋이 안 잡힘 / 비공개 레포 |
| `[오류]` | 레포 접근 불가 (삭제·비공개·주소 오타) |
| `[정상]` | 마감 후 변경 없음 |

`[확인]`이 가장 중요하다. 푸시는 마감 후인데 마감 후 커밋이 없다는 건
브랜치를 지웠거나 히스토리를 다시 썼다는 뜻일 수 있다.

**이 도구는 근거만 내놓고 탈락 여부를 판정하지 않는다.**
리베이스·머지처럼 악의 없는 작업으로도 커밋 시각이 밀리고, `[위반]`으로
찍힌 것이 README 오타 수정일 수도 있다. 판단은 운영진이 한다.

## 테스트

```bash
python test_check.py     # 또는 pytest
```

네트워크를 타지 않는 부분(URL 파싱, 판정 로직)만 검사한다.
**경계 테스트가 중요하다** — 09:59:59는 세이프, 10:00:00은 아웃.
한 칸 잘못 잡으면 정시에 낸 팀이 위반으로 찍힌다.

## 알아둘 것

- **비공개 레포는 404로 보인다.** 삭제·오타와 구분되지 않으므로
  `[오류]`로 나온 팀은 사람이 직접 확인해야 한다.
- **PR 머지 커밋도 잡힌다.** 마감 후 열려 있던 PR이 머지되면 위반으로 찍힌다.
- **자동 봇 커밋도 잡힌다.** dependabot 등이 돌고 있으면 그것도 올라온다.
- 검사 대상은 **모든 브랜치**다. 평가 기준은 main/master지만, 다른
  브랜치에 올린 것도 레포 수정이라 함께 보고한다.
- **오탐이 아니라 진짜로 잡힌다.** 공개 레포 40개로 시험하는 동안
  스냅샷과 대조 사이 5분 만에 실제 force-push 1건이 걸렸다.
